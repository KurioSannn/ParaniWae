# ADR-0003: Hardening autentikasi (verifikasi email, reset sandi, rate limit, IP klien)

Status: diterima (19 November 2026) · Melengkapi ADR-0002 · Tipe: PRODUCT-DECISION

## Keputusan
1. **Registrasi anti-enumerasi.** `POST /auth/register` selalu `202` dengan badan identik untuk email baru maupun terdaftar, tanpa sesi. Email baru menerima tautan verifikasi; email yang sudah ada menerima pemberitahuan "percobaan pendaftaran". Hash Argon2 selalu dihitung agar waktu respons mirip. Login baru diizinkan setelah email diverifikasi (`403 EMAIL_NOT_VERIFIED` hanya bila kredensial benar).
2. **Token sekali pakai** (`auth_tokens`): 256-bit acak, hanya SHA-256 yang disimpan, kedaluwarsa (verifikasi 48 jam, reset 30 menit), `used_at` sekali pakai, token lama sejenis dibatalkan saat token baru diterbitkan, pesan galat sama untuk salah/kedaluwarsa/terpakai/jenis salah. Reset sukses: sandi diganti, **semua sesi dicabut**, penguncian akun dibuka, email ditandai terverifikasi. Permintaan reset selalu `202` identik.
3. **Rate limit di PostgreSQL** (`rate_limits`, jendela tetap, upsert atomik `ON CONFLICT`): konsisten lintas worker/instance tanpa Redis. Kunci di-hash (tanpa PII). Cakupan: login/IP, register/IP, reset/IP + reset/email, verifikasi/IP, kirim-ulang/email, ubah-pengguna oleh admin/user. `429` + `Retry-After`. Ditambah penguncian per-akun yang sudah ada. Batas: jendela tetap membolehkan lonjakan di perbatasan jendela; cukup untuk MVP.
4. **IP klien aman dari pemalsuan.** `X-Forwarded-For` hanya dipakai bila peer langsung ada di `TRUSTED_PROXY_CIDRS`, dan IP diambil dari entri ke-`TRUSTED_PROXY_HOPS` **dari kanan** (ditambahkan proxy kita; entri kiri dari klien diabaikan). Default tanpa proxy tepercaya. **Temuan terukur (19 Nov 2026):** proxy rewrite Next.js TIDAK menimpa/menambah `X-Forwarded-For` secara tepercaya — pada konfigurasi awal yang mempercayai CIDR privat, XFF palsu dari klien menghasilkan kunci rate-limit sendiri (batas dapat dilewati). Default Compose kini **kosong**; di dev semua klien memakai IP container frontend sebagai kunci (batas global, tidak dapat dipalsukan). Regresi dijaga di `tests/e2e_flow.py` (probe XFF palsu lewat rantai proxy nyata). **Produksi:** per-klien hanya di belakang reverse proxy/LB yang **menimpa** XFF; isi CIDR + hop sesuai topologi nyata dan verifikasi dengan probe yang sama.
5. **Provider email abstrak.** `dev_sink` (hanya `APP_ENV=development`: email disimpan di `outbox_emails`, **tidak dikirim**, dapat dibaca di `/dev/mailbox`) dan `smtp` (SMTP standar). Tanpa provider valid, fitur terkait `503` — sistem tidak berpura-pura mengirim. Produksi menolak `dev_sink` (start gagal) dan `dev_sink` dianggap tidak terkonfigurasi di luar development.
6. **Redirect login aman.** `?next=` hanya path internal berawalan allowlist (`/app`, `/academy`, `/heritage`, `/community`, `/status`); ditolak: URL eksternal, `//`, backslash, kontrol/spasi, varian ter-encode, path di luar allowlist. Layout `/app` mengetahui path asal lewat `proxy.ts` (header internal yang selalu ditimpa).
7. **Fail closed.** Produksi gagal start bila cookie tidak Secure, `EXPOSE_DEMO_DATA=true`, sandi DB default/lemah, atau `MAIL_PROVIDER=dev_sink`. Seed demo menolak berjalan di luar development (staging butuh `ALLOW_DEMO_CONTENT_SEED=true` dan tetap tanpa akun demo).

## Dampak
Registrasi tidak lagi auto-login (UX +1 langkah); akun yang sudah ada saat migrasi ditandai terverifikasi. Ketergantungan baru pada konfigurasi proxy/email di produksi.

## Belum ada / risiko tersisa
MFA; CAPTCHA/deteksi bot; rate limit berbasis perangkat; ubah-sandi saat login; notifikasi login baru; rotasi sesi berkala; pengiriman email SMTP belum diuji terhadap server SMTP nyata (hanya dev_sink); timing pengiriman email dapat membedakan email baru/lama bila SMTP lambat (mitigasi: kirim via antrean/background — belum ada).
